# Complete Corpus Analysis

이 문서는 `docs/source-inventory.md`의 65개 파일을 모두 읽고 도출한 설계
해석입니다. 원본의 문장을 그대로 복제하기보다, 반복되는 운영 원칙과 서로
다른 자료 사이의 긴장 관계를 템플릿 결정으로 변환합니다.

## 1. 자료 구조가 말하는 채택 순서

전체 자료는 의도적으로 세 층으로 구성되어 있습니다.

1. 12개 강의가 실패 원인과 원칙을 설명합니다.
2. 최소 템플릿과 참고 문서가 바로 복사할 운영 산출물을 제공합니다.
3. 고급 팩·SOP·실습이 규모가 커질 때의 승격 경로와 비교 실험을 제공합니다.

따라서 스타터도 처음부터 고급 팩 전체를 강제하면 안 됩니다. 최소 팩으로
웜 스타트를 만들고, 관찰된 실패나 규모 조건이 생길 때만 다음 층을
활성화해야 합니다.

근거: `SRC-IDX-001`, `SRC-RES-001`, `SRC-REF-003`,
`SRC-ADV-001..002`, `SRC-PRJ-001..007`.

## 2. 하네스의 두 가지 분류 축

강의 2는 하네스를 `지시·도구·환경·상태·피드백`으로 설명합니다. 스킬
인덱스는 `지침·상태·검증·범위·세션 수명주기`를 핵심 하위 시스템으로
설명합니다. 모순이라기보다 서로 다른 축입니다.

- **역량 축**: 에이전트가 무엇을 보고, 실행하고, 관찰할 수 있는가
- **운영 통제 축**: 무엇을 선택하고, 언제 완료하며, 어떻게 이어받는가

스타터 감사는 둘 중 하나만 검사하면 안 됩니다. 예를 들어 테스트 도구가
있어도 완료 게이트에 연결되지 않으면 피드백은 있지만 통제가 없습니다.
반대로 WIP=1 규칙이 있어도 실행 가능한 환경이 없으면 통제만 있고 역량이
없습니다.

근거: `SRC-CH-001..002`, `SRC-SKL-001`.

## 3. 저장소는 발견 가능한 운영 기록이어야 한다

중요한 프로젝트 지식은 채팅·티켓·사람의 기억이 아니라 저장소 안에서
찾을 수 있어야 합니다. 다만 “더 많은 문서”가 목표는 아닙니다. 코드와
가까운 짧은 현재 문서, 명확한 색인, 생성 출처, 폐기 상태가 필요합니다.

콜드 스타트의 최소 질문은 다음 다섯 가지입니다.

1. 이 시스템은 무엇인가?
2. 어떻게 구성되어 있는가?
3. 어떻게 시작하는가?
4. 어떻게 검증하는가?
5. 지금 어디에 있고 다음은 무엇인가?

이 다섯 질문을 새 세션이 저장소만으로 답하지 못하면, 템플릿 채택이
완료되지 않은 것입니다.

근거: `SRC-CH-003`, `SRC-REF-004`, `SRC-ADV-004..005`,
`SRC-ADV-013..019`, `SRC-ADV-024`.

## 4. 루트 지침은 라우터이지 백과사전이 아니다

루트 파일에는 목적, 시작·검증 경로, 협상 불가 제약, 상태 산출물, 종료
규칙만 남겨야 합니다. 주제별 구현 세부사항은 적용 조건과 함께 더 가까운
문서로 라우팅합니다. 규칙에는 최소한 다음 메타데이터가 필요합니다.

- 출처 또는 추가 이유
- 적용 조건
- 제거·재검토 조건
- 가능하면 기계적 검사

원본은 50~200줄 정도를 경험적 가이드로 제시하지만, 스타터는 줄 수 자체를
절대 규칙으로 만들지 않습니다. 중요한 것은 신호 대 잡음비와 발견 비용입니다.

근거: `SRC-CH-004`, `SRC-REF-005..006`, `SRC-ADV-003`,
`SRC-ADV-012`.

## 5. 상태는 기계 진실과 인간 인계를 분리하되 중복하지 않는다

자료는 기능 목록, 진행 로그, 결정 로그, 핸드오프, Git 체크포인트를
권장합니다. 모두 유용하지만 작은 저장소에서 각각을 무조건 두면 상태가
중복됩니다.

Lite의 해석:

- `feature_list.json`: 범위·우선순위·상태·검증·증거의 기계 진실
- `docs/STATE.md`: 현재 목표·최근 검증·위험·다음 행동의 bounded human snapshot
- 설계 근거가 내구적으로 필요할 때만 ADR/결정 문서로 승격
- Git 이력은 변경 체크포인트지만, 문서화되지 않은 현재 상태의 대체물이 아님

이 구조는 짧은 작업에서 불필요한 핸드오프 파일을 만들지 않으면서도 긴
작업의 재구축 비용을 낮춥니다.

근거: `SRC-CH-003`, `SRC-CH-005`, `SRC-TPL-003`,
`SRC-TPL-010`, `SRC-ADV-007`, `SRC-ADV-014..016`.

## 6. 초기화와 구현을 분리한다

최초 채택 단계의 산출물은 비즈니스 기능이 아니라 다음 운영 기반입니다.

- 재현 가능한 설치·시작 경로
- 최소 하나의 실제 통과 검증
- 현재 범위와 다음 작업
- 새 세션이 읽을 상태
- 안전한 체크포인트

다만 작은 기존 프로젝트의 단일 로컬 수정까지 매번 전체 초기화로
승격시키면 오버헤드가 큽니다. 구현 단계에서는 변경이 단일·로컬·가역적이고
공유 계약·상태·검증·외부 효과를 건드리지 않을 때만 축약 프리플라이트를
허용하는 것이 합리적입니다.

근거: `SRC-CH-006`, `SRC-TPL-008`, `SRC-REF-001`,
`SRC-REF-004`, `SRC-PRJ-002`.

## 7. 범위 제어의 기본값은 WIP=1이다

동시에 여러 기능을 활성화하면 추론 예산이 분산되고 검증되지 않은 반제품이
쌓입니다. 기능 항목은 한 세션 안에 검증 가능한 크기로 나누며, 하나를
통과시키거나 명시적으로 차단한 후 다음을 활성화합니다.

병렬 작업이 필요한 경우에도 전역 WIP를 무작정 늘리지 않습니다. 서로
겹치지 않는 파일·상태·검증 소유권을 가진 독립 작업으로 격리하고, 통합
게이트에서 다시 직렬화해야 합니다.

근거: `SRC-CH-007`, `SRC-CH-008`, `SRC-TPL-001..002`,
`SRC-TPL-006`, `SRC-PRJ-004..005`.

## 8. 기능 목록은 실행 가능한 계약이다

각 항목에 필요한 최소 정보:

- 안정적인 ID와 우선순위
- 사용자 또는 시스템이 관찰할 동작
- 현재 상태
- 실제 실행할 검증
- 증거
- 차단 이유와 다음 재검토 조건
- 설계·요구사항 근거

원본은 `passing`을 비가역 상태로 설명하지만, 실제 소프트웨어는 회귀할 수
있습니다. Lite에서는 이전 증거를 보존하면서 재검증 실패 시 `active` 또는
`blocked`로 강등할 수 있어야 합니다. 비가역성은 감사 이력에 적용하고,
현재 진실에는 적용하지 않습니다.

근거: `SRC-CH-008`, `SRC-TPL-006..007`.

## 9. 완료는 자신감이 아니라 위험에 맞는 실행 증거다

검증은 비용이 싼 것부터 비싼 것으로 진행합니다.

1. 문법·정적 분석
2. 집중 단위·계약 테스트
3. 시작·런타임·통합 검증
4. 사용자 또는 시스템의 엔드투엔드 여정
5. 위험에 따른 성능·보안·복구 검증

원본은 E2E를 강하게 강조하지만 모든 문서 수정이나 로컬 유틸리티에 E2E를
강제하면 느리고 취약한 하네스가 됩니다. 크로스 컴포넌트·사용자 대면·외부
효과가 있는 변경에는 E2E가 필수이고, 그 외에는 범위와 위험에 맞는 가장
강한 실행 증거를 선택합니다. 생략한 레벨과 이유도 증거에 기록합니다.

오류 메시지는 `무엇이 실패했는가 / 왜 중요한가 / 어디서 어떻게 고칠
것인가`를 포함해야 자기 수정 루프가 됩니다.

근거: `SRC-CH-009..010`, `SRC-TPL-005`,
`SRC-ADV-006`, `SRC-ADV-023`, `SRC-PRJ-006`.

## 10. 역할 분리는 선택형 독립성 장치다

생성자가 자신의 작업을 평가하면 낙관 편향이 생길 수 있습니다. 고위험,
주관적 품질, 복잡한 크로스 컴포넌트 변경에서는 계획·생성·평가 역할을
분리하는 편이 낫습니다.

그러나 모든 작은 작업에 다중 에이전트를 기본 설치하면 비용·지연·조율
표면이 커집니다. Lite 코어는 고정 루브릭과 독립 검증 명령을 제공하고,
역할 분리는 평가 편향이 실제로 관찰되거나 위험 임계값을 넘을 때 활성화합니다.

근거: `SRC-CH-009`, `SRC-TPL-005`, `SRC-SKL-001`,
`SRC-PRJ-006`.

## 11. 관측 가능성은 점진적으로 추가한다

기본적으로 필요한 것은 재현 가능한 시작, 구조화된 실패 출력, 핵심 여정의
상태 신호입니다. 로그만으로 설명되지 않는 다단계·분산 흐름이 있을 때
메트릭과 트레이스를 추가합니다. OpenTelemetry는 좋은 표준화 선택이지만
모든 저장소의 기본 의존성은 아닙니다.

프로세스 관측도 필요합니다. 작업 전 범위·제외·통과 기준을 적고, 작업 후
같은 기준으로 판단해야 재시도가 무작위가 되지 않습니다.

근거: `SRC-CH-011`, `SRC-ADV-010`, `SRC-ADV-027`,
`SRC-PRJ-005`, `SRC-PRJ-007`.

## 12. 세션 종료와 하네스 자체의 유지보수

클린 상태는 단순히 Git 워킹 트리가 비어 있다는 뜻이 아닙니다.

- 필요한 빌드·테스트가 통과함
- 현재 범위와 증거가 기록됨
- 임시 산출물과 무음 실패가 없음
- 표준 시작 경로가 재실행 가능함
- 다음 행동 또는 차단 조건이 명확함

실패한 작업을 억지로 초록 상태로 만들 수 없다면, 마지막 검증 체크포인트로
롤백하거나 실패 상태와 재현 명령을 명시적으로 남겨야 합니다. 파괴적
자동 정리는 기본값으로 두지 않습니다.

하네스도 부패하므로 구성 요소마다 재검토 트리거가 필요합니다. 고정된
벤치마크로 하나씩 제거해 품질이 떨어지지 않는 구성은 삭제하는 절제
실험이 장기 유지보수의 핵심입니다.

근거: `SRC-CH-012`, `SRC-TPL-004`, `SRC-TPL-009`,
`SRC-ADV-009`, `SRC-PRJ-007`.

## 13. 보안과 권한은 별도 필수 축이다

강의의 5개 하위 시스템만 따르면 도구 접근성을 강조하다가 권한 경계가
약해질 수 있습니다. 고급 팩은 비밀, 신뢰할 수 없는 입력, 외부 행동,
의존성 검토를 별도 문서로 둡니다.

Lite 코어에는 최소한 다음 원칙이 있어야 합니다.

- 비밀은 파일과 로그에 쓰지 않음
- 외부·파괴적 동작은 명시적 권한 필요
- 읽기 전용 진단과 변경 권한 구분
- 명령은 배열 또는 안전한 인자로 실행하고 임의 문자열 평가를 피함
- 새 의존성은 필요성과 유지 비용을 기록

근거: `SRC-CH-002`, `SRC-ADV-011`.

## 14. 채택하지 않는 것

다음은 유용할 수 있지만 Lite 기본값으로 채택하지 않습니다.

- 모든 프로젝트에 고정된 `Types -> Config -> Repo -> Service -> Runtime -> UI`
  계층: 예시 규범이며 프로젝트별 아키텍처와 충돌할 수 있음
- 모든 세션의 전체 OpenTelemetry 수집: 작은 저장소에는 과도함
- 모든 작업의 플래너·생성자·평가자 3역할: 비용과 지연이 큼
- 모든 파일을 처음부터 생성하는 고급 팩: 발견 비용과 유지 표면이 커짐
- 원본 강의의 성공률·시간·비용 수치: 최신 검증 없이 템플릿 계약으로
  사용하지 않음
- `passing` 상태의 비가역성: 현재 진실보다 이력 보존을 우선해야 함

이 선택은 원칙을 버리는 것이 아니라, 관찰된 필요에 따라 승격하는
점진적 공개 전략입니다.
