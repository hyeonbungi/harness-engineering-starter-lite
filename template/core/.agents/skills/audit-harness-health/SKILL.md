# Harness Health Audit

## 목적

이 스킬은 시간이 지나도 이 프로젝트가 처음 채택한 에이전트 행동 양식,
하네스 엔지니어링과 작업 루프의 핵심 계약을 실제 저장소 증거로 점검합니다.
문서가 존재한다는 사실과 실제로 강제되는 동작을 구분하고, 확인하지 못한
내용은 `미확인`으로 남깁니다.

이 스킬은 제품·언어·프레임워크·CI·클라우드를 가정하지 않습니다.

## 언제 사용하나요?

- 사용자가 `$audit-harness-health`, `/audit-harness-health` 또는 같은 의미의
  하네스 건강 감사를 요청합니다.
- 동일한 에이전트 오류, 완료 오판, 상태 불일치 또는 루프 실패가 반복됩니다.
- 에이전트·모델·런타임·권한·릴리스·대규모 마이그레이션이 바뀝니다.
- 지침과 검사가 누적되어 느려졌거나 서로 모순된다고 의심됩니다.
- Core 구성 요소를 유지·통합·교체·제거할 근거가 필요합니다.

한 파일의 오탈자, 일반 제품 코드 리뷰 또는 이미 원인이 분명한 단일 실패에는
전체 감사를 실행하지 않습니다. 관련 계약이 위험할 때만 좁은 관점으로
점검합니다.

## 읽기 전용 경계

이 스킬을 호출한 감사 자체는 **읽기 전용**입니다.

- 파일·상태·Git·설정·의존성·외부 시스템을 변경하지 않습니다.
- 상태 전환, 자동 자기개선, 설치, setup, commit, push와 배포를 수행하지
  않습니다.
- 제품 명령이나 네트워크 요청을 실행하지 않습니다.
- 경고를 수정 권한으로 확대하지 않습니다.
- 사용자가 별도로 수정을 요청했다면 감사를 먼저 끝내고, 확인된 결함만 일반
  변경 계약과 WIP=1에 따라 별도 단계에서 처리합니다.

감사 전후 `git status --short`를 비교합니다. 감사 때문에 상태가 바뀌면 그
자체를 결함으로 보고하고 추가 실행을 중단합니다.

## 감사 깊이 선택

기본은 **빠른 감사**입니다.

| 깊이 | 사용 조건 | 범위 |
| --- | --- | --- |
| 빠른 감사 | 일반 호출, 반복 실패의 첫 점검 | 현재 지침·상태·active 기능·기계 audit |
| 집중 감사 | 문제 영역이 알려짐 | agent, harness, loop, evidence, skills, lifecycle 중 관련 영역 |
| 깊은 감사 | 릴리스·대규모 변경·광범위 드리프트 | 빠른 감사 + 관련 원장·설치 manifest·Git 증거 |

전체 원본 Source 맵, 과거 영수증과 Git 이력은 현재 드리프트를 설명할 때만
읽습니다. `./init.sh` 또는 `init.ps1`은 제품별 gate나 캐시를 실행할 수 있으므로
감사에서 자동 실행하지 않습니다. 사용자가 전체 검증까지 요청했고 현재 계약상
안전할 때만 별도 검증으로 실행합니다.

## 실행 순서

1. 저장소 루트를 확인하고 감사 전 `git status --short`를 기록합니다.
2. 적용 범위의 `AGENTS.md`, `docs/STATE.md`와 `feature_list.json`의 active 또는
   다음 기능 레코드만 먼저 읽습니다.
3. 아래 기계 감사를 저장소 루트에서 한 번 실행합니다.

```bash
python3 scripts/harness.py audit
```

4. 선택한 영역에 필요한 가까운 파일만 추가로 읽습니다.
5. 기계 감사 결과를 그대로 결론으로 복사하지 말고, 아래 핵심 계약과 실제
   파일·Git 증거를 대조합니다.
6. 감사 후 `git status --short`를 다시 확인합니다.
7. 확인된 결함, 경고와 미확인 항목을 구분해 한국어 존댓말로 간결하게
   보고합니다.

Python 명령은 현재 init 어댑터가 선택하는 Python 3.10+를 우선합니다.
Windows에서 `python3`가 없다면 프로젝트의 `init.ps1`이 선택하는 `py -3` 또는
`python`을 사용하되 감사 외 명령은 실행하지 않습니다.

## 핵심 계약

### Agent

- 루트 지침은 짧은 라우터이고 세부 규칙은 가까운 문서에 있습니다.
- 사용자에게 한국어 존댓말로 쉽고 간결하게 설명합니다.
- 사실·추론·제안, 구현·검증·배포 상태를 구분합니다.
- 반복·재현 가능한 구조 결함만 한 번 자동 개선하며 명시적 읽기 전용·중지와
  제품·외부·파괴적 경계를 넘지 않습니다.
- 항상 읽는 파일이 상한을 넘거나 같은 규칙을 중복 보유하지 않습니다.

### Harness

- 명령은 셸 문자열이 아닌 인자 배열이며 cwd·timeout·출력 상한이 있습니다.
- 비밀은 파일·명령 인자·로그·영수증에 저장하지 않습니다.
- 설치 manifest와 구성 요소 원장이 실제 관리 파일을 정확히 소유합니다.
- 특정 제품 스택이나 선택형 관측·다중 에이전트 기능을 Core에 강제하지
  않습니다.
- 검사 제거나 상한 증가로 실패를 숨기지 않습니다.

### Loop

- active 기능은 최대 하나이고 현재 상태 문서와 기계 원장이 일치합니다.
- passing은 실제 gate binding과 현재 유효한 증거를 요구합니다.
- 재시도·timeout·중단·재개·rollback·종료 조건이 명시되어 있습니다.
- 기능 이력과 영수증 참조는 bounded하며 실제 영수증 파일은 보존합니다.
- 자동 개선과 반복 루프는 예산과 종료 조건이 있고 연쇄적으로 자신을
  확장하지 않습니다.

### Skills와 수명주기

- 정본은 `.agents/skills/audit-harness-health/SKILL.md` 한 곳입니다.
- `.claude` 진입점은 정본을 읽는 짧은 포인터이며 감사 규칙을 복제하지
  않습니다.
- `.agents/skills`를 직접 탐색하지 않는 다른 클라이언트도 실제 채택할 때만
  같은 형식의 짧은 포인터를 추가합니다.
- Skill의 이름·설명·포인터 대상과 Core validator가 함께 변경됩니다.
- upgrade·remove는 manifest 소유권과 로컬 수정 보호를 유지합니다.

## 판정 규칙

- `healthy`: 선택한 정적 계약에서 결함을 찾지 못했습니다. 미확인 런타임
  행동이 없다는 뜻은 아닙니다.
- `degraded`: 파일이나 실행 결과로 재현되는 계약 위반이 있습니다.
- `unknown`: 필수 파일·런타임·권한이 없어 신뢰할 수 있게 확인하지 못했습니다.

문서만으로 에이전트의 실제 준수, 권한 강제, 실제 timeout 종료, 평가자 독립성,
제품 E2E와 구성 요소의 비용 대비 가치를 증명하지 않습니다. 필요한 경우 실제
작업 trace, 현재 영수증, 네이티브 플랫폼 실행 또는 절제 실험을 요구합니다.

## 결과 형식

1. 결론: `healthy` / `degraded` / `unknown`, 선택한 감사 깊이
2. 확인된 문제: 심각도, 위치, 현재 증거, 영향, 가장 작은 수정, 트레이드오프,
   검증과 rollback
3. 경고: 정적 신호이지만 결함으로 확정하지 못한 내용
4. 미확인: 필요한 실제 환경이나 증거
5. 실행 증거: 실행한 읽기 전용 명령과 종료 코드, 감사 전후 Git 상태 일치

문제가 없다면 개선점을 억지로 만들지 않습니다. 전체 로그나 전체 원장을
응답에 붙이지 않고 핵심 수치와 관련 경로만 제시합니다.
