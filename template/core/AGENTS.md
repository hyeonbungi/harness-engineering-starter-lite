# AGENTS.md

이 저장소는 장기 실행 코딩 에이전트가 저장소만으로 안전하게 작업을
시작·검증·인계할 수 있도록 구성되어 있습니다. 이 파일은 짧은 라우터로
유지하고 세부 정보는 연결된 문서에 둡니다.

## 요청 분류

현재 메시지의 명시적 의도를 우선합니다.

- 답변: 읽고 답하되 파일을 변경하지 않습니다.
- 진단: 필요한 범위의 읽기 전용 재현까지만 수행합니다.
- 제안: 선택지와 트레이드오프를 설명하되 구현하지 않습니다.
- 실행: 요청된 범위만 변경하고 필요한 검증까지 수행합니다.

과거 승인이나 우연히 발견한 드리프트만으로 현재 요청을 실행으로
승격하지 않습니다.

## 자동 구조 개선

다만 에이전트 행동 양식, 하네스 또는 작업 루프에서 반복되거나 재현 가능한
구조적 결함을 확인하면 별도 사용자 명령 없이도 저장소 내부에서 자동으로
개선합니다. 이는 답변·진단·제안 요청의 제품 변경 금지에 대한 좁은 예외입니다.

- 변경 전에 근거와 개선 범위를 사용자에게 짧게 알리되 승인을 기다리지
  않습니다.
- 사용자 정정, 동일 실패 재발, 문서·실행 불일치와 최종 응답 직전에 자동
  개선 발동 조건을 확인합니다.
- 사용자가 이번 요청에서 변경 금지·중지·읽기 전용을 명시하면 자동 개선도
  수행하지 않습니다.
- 제품 동작, 외부 시스템, 비밀·권한, 파괴적 작업, 커밋·푸시·배포는 자동
  권한에 포함하지 않습니다.
- 한 사용자 작업에서 자동 개선 루프는 최대 한 번만 실행하고, 기존
  `BOOT-001` 또는 동등한 하네스 유지보수 기능을 WIP=1 규칙으로 재개합니다.
- 자세한 트리거·WIP·검증·종료 계약은 `docs/COMMUNICATION.md`를 따릅니다.
- 하네스 철학 전반의 건강 점검은 `$audit-harness-health`를 호출합니다. 해당
  감사 중에는 자동 개선을 수행하지 않고, 확인된 결함의 수정은 감사 종료 뒤
  별도 변경 단계로 분리합니다.

## 사용자 커뮤니케이션

- 사용자에게는 항상 한국어와 존댓말로 답합니다.
- 컴퓨터공학과 대학생이 이해할 수 있게 어려운 용어를 처음 한 번 쉽게
  설명하고, 결론과 현재 상태를 먼저 간결하게 전달합니다.
- 사실·추론·제안과 구현·검증·커밋·푸시·배포 상태를 구분합니다.
- 표·흐름도·트리는 관계나 순서를 실제로 더 쉽게 만들 때만 사용합니다.
- `docs/COMMUNICATION.md`는 일반 시작에서는 미리 읽지 않고, 복잡한 보고·
  자기개선 판단 또는 현재 작업과 직접 관련된 경우에만 읽고 적용합니다.

## 시작 순서

실행 작업 전에:

1. `pwd`로 저장소 루트를 확인합니다.
2. `docs/STATE.md`에서 현재 검증 상태와 다음 행동을 읽습니다.
3. POSIX에서는 `./init.sh`, Windows PowerShell에서는 `.\init.ps1`을 한 번
   실행합니다.
4. init 출력의 bounded `cold-start-summary`에서 현재 기능을 찾고, 전체 기능·
   Source·영수증 원장 대신 `feature_list.json`의 그 기능 레코드만 확인합니다.
   별도 `cold-start --json`은 기계 재조회가 필요한 경우에만 실행합니다.
5. 변경 대상과 직접 관련된 `docs/ARCHITECTURE.md`, `docs/VALIDATION.md` 또는
   `docs/COMMUNICATION.md`만 추가로 읽습니다.

## 작업 규칙

- 한 번에 하나의 기능만 `active`로 둡니다.
- init 어댑터가 선택한 Python으로 `scripts/harness.py state ...`를 실행해
  상태를 전환합니다.
- 기능 완료는 같은 Python으로
  `scripts/harness.py complete <ID> --risk <PROFILE>`을 실행해 검증하고
  기록합니다.
- 각 기능의 `verification.bindings`를 실제 gate ID에 연결하고, 신선도 판단에
  필요한 정확한 제품·테스트 파일을 `tracked_files`에 둡니다.
- 실행 증거 없이 `passing`을 주장하지 않습니다.
- 검증을 통과시키기 위해 검사를 삭제하거나 약화하지 않습니다.
- 범위 밖 문제는 기록하되 위 자동 구조 개선 예외가 아니면 현재 작업에
  포함하지 않습니다.
- 비밀을 파일·명령 인자·로그에 넣지 않고 환경 변수와 최소 권한을 사용합니다.
- 외부·파괴적 행동은 명시적 사용자 승인을 받은 뒤 수행합니다.
- 반복되는 리뷰 의견은 가능한 경우 작고 실행 가능한 검사로 승격합니다.
- 구조적 결함의 자기개선은 `docs/COMMUNICATION.md`의 권한·종료 조건을
  따르고, 새 규칙을 누적하기보다 기존 규칙을 통합하거나 교체합니다.
- 구현 중에는 변경과 연결된 집중 검사를 우선하고, 필요한 전체 위험 게이트는
  완료 시 한 번 실행합니다.

## 복수 에이전트 작업

사용자가 복수 에이전트 또는 병렬 작업을 명시적으로 요청한 경우에만
`docs/AGENT_COORDINATION.md`를 읽습니다. 일반 작업에서는 에이전트를 자동으로
생성하지 않습니다. 병렬 worker는 하나의 active 기능 아래에서 문서의 격리·
소유권·인계·lead 직렬 통합 계약을 따릅니다. lead는 가장 작은 worker 수만
사용하고 worker는 하위 에이전트를 생성하지 않습니다.

## 상태와 문서

- `harness.config.json`: 안전한 명령 배열과 위험별 검증 프로필
- `feature_list.json`: 범위·상태·검증·증거의 기계 진실
- `docs/STATE.md`: 현재 목표·검증 상태·위험·다음 행동
- `docs/ARCHITECTURE.md`: 시스템 지도와 의존성 경계
- `docs/VALIDATION.md`: 단계별 완료 게이트와 황금 여정
- `docs/COMMUNICATION.md`: 사용자 설명·시각화·증거 보고·자기점검 계약
- `docs/AGENT_COORDINATION.md`: 요청된 병렬 작업의 격리·소유권·인계·통합 계약
- `docs/harness/components.json`: 하네스 구성 요소와 근거

## 완료 기준

변경은 다음을 모두 만족할 때만 완료입니다.

- 요청된 동작이 구현되었습니다.
- 위험 프로필이 요구하는 모든 게이트를 실행했습니다.
- 기능에 연결된 모든 gate가 실행되었고 최신 성공 영수증의 설정·검증·파일·
  OS/Python runtime digest가 현재 상태와 일치합니다.
- `feature_list.json`과 `docs/STATE.md`가 현재 사실과 일치합니다.
- 임시 산출물이 없고 표준 시작 경로가 재실행 가능합니다.

## 종료 순서

1. 기능 상태와 증거를 갱신합니다.
2. `docs/STATE.md`를 현재 사실만 남도록 갱신합니다.
3. 필요한 위험 프로필로 검증합니다.
4. 임시 파일과 미설명 변경을 남기지 않습니다.
5. 커밋·푸시·배포는 사용자 요청과 저장소 정책에 따라 수행합니다.
